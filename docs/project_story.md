# FunRec PyTorch 算法项目故事

## 当前一句话版本

将 FunRec 的 YouTubeDNN 召回和 DeepFM 排序从 TensorFlow 迁移到 PyTorch，完成离线训练、工件部署、在线推理和前端体验；随后通过严格时序评估、分层误差诊断和控制变量实验，对召回—排序—重排全链路进行算法优化。

## 故事状态

### 已完成：工程迁移

- PyTorch YouTubeDNN。
- PyTorch DeepFM。
- GPU 训练与 checkpoint 恢复。
- 本地部署工件。
- 在线召回与排序。
- Docker Compose 全栈运行。
- 前端真实体验。

### 进行中：可信 Baseline

- 审计数据切分和负采样。
- 建立独立 Train/Validation/Test。
- 统一召回、排序和系统指标。
- 保存可追溯实验工件。

### 尚未决定：第一个优化方向

不会预设 Hard Negative、Attention 或新模型。先按用户活跃度、物品热门度、类型偏好和推荐漏斗进行诊断，再依据证据强度、预期收益、实现成本和面试解释价值选择方案。

## 面试主线草案

1. 为什么迁移：统一 PyTorch 技术栈、GPU 支持与可维护性。
2. 如何保证等价：模型单元测试、训练 smoke test、工件恢复和在线输出验证。
3. 为什么现有指标还不够：发现 Validation/Test 复用与采样评估口径问题。
4. 如何建立可信实验：严格时序三段切分和统一指标体系。
5. 如何定位瓶颈：用户、物品和推荐漏斗切片。
6. 如何提出方案：由误差证据推导假设，不先套模型。
7. 如何验证：控制变量、消融实验、三随机种子复验。
8. 如何落地：部署最佳工件并测量端到端精度与延迟。

## 证据规则

PPT 中的每个数字必须能够追溯到 `experiment_registry.md`、机器生成的 metrics、训练日志、checkpoint 和 Git commit。失败实验同样保留，用于解释判断过程。
